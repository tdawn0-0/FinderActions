# ADR 0001: Authenticated Host IPC

Date: 2026-10-02. Status: **Recommendation, needs maintainer sign-off**.

## Context

The nonsandboxed Developer ID Host executes user actions. FinderSync is sandboxed; Settings is a separate nonsandboxed helper. Distributed notifications authenticate neither execution requests nor menu snapshots. Plan 005 now checks versions, counts, paths, enabled actions and selection filters, but a same-user sender can still request permitted actions. Plan 009 removed unreachable shared snapshot files; the extension retains its own last-live cache. Neither change authenticates peers.

The spike investigates mutual NSXPC peer requirements without changing production code, signing identities, preferences, the installed application or Finder. Distribution remains Developer ID, not App Store. Authentication must cover both execution and snapshot responses; authenticating only request senders leaves menu substitution possible.

## Options considered

| Option | Advantages | Costs and entitlements |
| --- | --- | --- |
| A. Launchd-managed Host via `SMAppService.agent(plistName:)`, advertising a Mach service | One resident application process; stable rendezvous and launchd demand activation | Changes Host launch/lifecycle, status item, manual launch, login and quit semantics. Package an agent plist under `Contents/Library/LaunchAgents`. Sandbox client needs an App Group service namespace or a specific Mach lookup exception. Host must accept connections before readiness and avoid duplicate instances. Actual AppKit/FinderSync deployment unproven. |
| B. Separate tiny helper LaunchAgent | Keeps ordinary Host app launch; dedicated rendezvous and lifecycle | Extra binary/process and authenticated helper↔Host hop, resource cost and ownership complexity. Do not move execution/FDA responsibility accidentally. Same client entitlement choices as A; helper must check exact allowed clients and Host. |
| C. Anonymous Host listener with exchanged `NSXPCListenerEndpoint` | Keeps normal app; no named listener in Host | An endpoint still needs a bootstrap channel and restart rediscovery. An unauthenticated notification or writable file carrying the endpoint is not sufficient authentication. Require peer checks and a harmless handshake; sandbox access and endpoint exchange remain untested. An authenticated broker adds B's cost. |

A normal app cannot assume that naming an `NSXPCListener` advertises a discoverable service. Its named initializer expects a service advertised in a launchd plist. Embedded XPC services offer another packaging mechanism, but do not by themselves establish FinderSync→already-running Host rendezvous. [Apple NSXPCListener](https://developer.apple.com/documentation/foundation/nsxpclistener), [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice).

For release, prefer an App Group entitlement on the communicating targets and a service name `<group identifier>.<unique name>`. Apple currently supports registered `group.*` IDs **and** macOS `<TEAMID>.<group name>` IDs; the latter do not require developer-portal registration. A group namespace controls sandbox reachability, not which action a peer may perform. Keep code requirements and request validation as separate gates. An exact `com.apple.security.temporary-exception.mach-lookup.global-name` is an experimentally working fallback, not an assertion of App Store approval. [App Groups entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups), [Configuring app groups](https://developer.apple.com/documentation/xcode/configuring-app-groups), [Mach lookup exception](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/AppSandboxTemporaryExceptionEntitlements.html).

## Recommendation, needs maintainer sign-off

Advance A as the first integration experiment because it avoids an additional resident helper. Do **not** adopt it until a genuinely sandboxed FinderSync extension connects to the launchd-managed AppKit Host under release signing, and login/quit/relaunch behavior and memory satisfy product requirements. If A's UI lifecycle cannot be made reliable, evaluate B explicitly against the added footprint. C is not a shortcut around authenticated bootstrap.

Require mutually checked signatures before activation and a nonsensitive hello/reply before sending paths or trusting snapshots. Release requirements should restrict Apple-issued Developer ID Application signing, the actual Team ID, and the exact expected bundle identifier; use a client allowlist by role, not a team-wide wildcard. Validate the requirement against signed release artifacts and an incorrect identifier from the same team. Settings may request reloads but must not inherit Finder execution permissions. No release requirement or App Group is added by this ADR.

## Consequences

SMAppService registration is subject to user approval/status; denial must leave a clear recovery path. Agent registration bootstraps it for later logins, which differs from independently toggling main-app launch at login. Define whether “Quit” stops execution until the next explicit launch or allows demand activation; do not silently revive the Host after the user quits. [Apple register()](https://developer.apple.com/documentation/servicemanagement/smappservice/register()).

Ad-hoc signatures have no certificate chain, so `anchor apple generic` plus a Team-ID certificate condition does not pass. The experiment pins exact Debug CDHashes and regenerates them on rebuild. Never ship identifier-only or unconditional Debug requirements in Release. A local development certificate or generated exact-build trust manifest requires a separate design. Production nested signing/notarization must include the agent plist/helper and approved group entitlements; release scripts are unchanged here. [Code signing requirement language](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/RequirementLang/RequirementLang.html).

Migrate `docs/ipc.md` only with implementation: remove execute/snapshot notification consumers as well as publishers, define hello/schema negotiation, authenticated reconnect, cancellation, readiness, request IDs and failure reporting. An unauthenticated compatibility fallback would preserve the vulnerability. Keep plan 005's validator and deduplication after migration.

## Prototype results and six answers

Artifacts are isolated on **`spike/006-xpc-ipc`**, commit **`083ccef08d27c209fdefa031f3b3b77cf7c9900b`**, under `spike/006/`. Run `python3 spike/006/run.py`; `results.txt` records the final run. Environment: macOS 27.0 (26A428), arm64, Xcode 27.0 (27A266a). This is not macOS 15 validation.

The harness compiled a Foundation NSXPC server, advertised only `com.finderactions.spike006.ping` via an isolated temporary launchd agent, and sent ExecuteRequest-shaped JSON naming `/tmp`. It signed uniquely identified clients ad hoc and set exact CDHash requirements on both sides before `resume`. Its `finally` removed the agent; a subsequent `launchctl print` confirmed the service was absent. No FinderActions application was installed/replaced, no production extension registered, and no signing key or paid-account action used. Six prototype files are committed only on the spike branch; the ADR branch contains this document alone.

1. **Sandbox connectivity:** an isolated sandbox `.app` without lookup entitlement failed with Cocoa **4099**, lookup error **159 — Sandbox restriction**. The same client with an exact Mach lookup exception got `CLIENT_REPLY pong`. This establishes sandbox app reachability for the exception; genuine FinderSync-in-Finder connectivity and release Team-ID App Group access remain **unproven**. Initial bare sandbox executables trapped in `_libsecinit_appsandbox.cold.6` before Swift main; packaging app bundles resolved initialization. Installing a separate FinderSync bundle into Finder was deliberately omitted to avoid altering the user's extension state; a release-signed isolated FinderSync integration experiment remains required.
2. **Normal app/service vending:** launchd `MachServices` successfully launched the prototype listener on first client request. The experiment used `launchctl bootstrap`, not SMAppService or the actual Host AppKit executable. Options A–C above specify the remaining lifecycle questions. SMAppService registration and approval are **not tested**.
3. **Peer verification:** trusted client got pong; the mismatching ad-hoc client got Cocoa **4097** and its distinct request ID never reached the exported method. Error4097 alone is generic; the controlled trusted comparison and server method log support rejection. A client expecting an impossible server CDHash got Cocoa **4102 — The code signature requirement failed**. Thus both directions enforce requirements on messages in this setup. Crucially the server received that client's outgoing ping before the rejected reply: do a harmless hello before any path-bearing request. An actually unsigned client and Developer ID requirements were **not tested**. Apple documents this API from macOS13; it invalidates connections for messages that fail the requirement. [setCodeSigningRequirement](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement(_:)).
4. **Snapshots:** request/reply works with a String-shaped payload; a typed `getSnapshot` reply and optional authenticated callback over the same connection are plausible but **not prototyped**. Prefer asynchronous refresh with the last authenticated cache; never block synchronous Finder menu construction on an RPC. Host can invalidate/refresh subscribed clients on configuration changes; design ordering and reconnect explicitly. Remove distributed snapshot input when implemented.
5. **Launch/retry:** demand launch worked in this launchd harness. It can replace explicit app launch and the fixed delayed retry once registration, readiness and reconnect are proven. Connection interruption and lost replies still require a policy. Preserve request IDs/dedupe: a timeout does not prove that an execution failed, and automatic replay can double-run actions.
6. **Footprint:** minimal listener RSS after the cases was **8528KiB** (`ps -o rss`), a single sample of an artificial server. No total Host/Settings/FinderSync physical footprint, idle baseline, helper incremental cost or AppKit launch cost was measured. A does not add a separate resident helper; B does. The advertised memory target is **not validated** by this number. Measure idle/peak physical footprint and aggregate processes before committing to either architecture.

The recorded-output assertions checked two successful replies, all three negative errors, absence of untrusted/sandbox-denied method invocations and presence of the wrong-server outgoing request. Prototype JSON is inert; it does not execute scripts. No production build is claimed: direct Swift compilation exercised the isolated experiment instead of installing a production-identical Debug app.

## Implementation outline

1. Obtain maintainer sign-off on A versus B and explicit quit/login semantics. Test a unique isolated FinderSync bundle on macOS15 and the current OS with a Team-ID group service; validate Developer ID requirements and sandbox entitlement behavior.
2. Package an SMAppService launch agent with a unique development service first. Exercise denied approval, clean installation, upgrade, removal, login, manual app launch, service crash and readiness; measure all process footprints.
3. Define a Foundation-only typed XPC interface with nonsensitive hello, version negotiation, snapshot pull/callbacks and execute replies. Set exact peer requirements before resume, complete hello before paths, and keep validation/dedupe and role permissions.
4. Switch execute and snapshot traffic together. Test malicious clients, same-team wrong identifiers, wrong servers, forged notifications, retries with lost replies, stale caches and connection interruption. Delete both old unauthenticated consumers; retain only harmless notifications if justified.
5. Update packaging/signing/notarization and protocol/onboarding/troubleshooting docs after tests pass. Record memory and lifecycle results before claiming the footprint or launch behavior.
